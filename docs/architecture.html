line-bot-ledger — 系統架構圖

三個獨立 Cloud Run 服務（services/webhook 記帳、services/liff 記帳表單、services/summary 每日總結）+ LINE Messaging API/LIFF + Firestore（個人記帳練習專案）

CI/CD 身份
CI/CD 流程（虛線框）

① 即時記帳流程

  • 使用者在 LINE 傳送記帳訊息
  • LINE Platform 以 HTTPS POST 呼叫 services/webhook 的 /callback
  • 驗證 X-Line-Signature，用 ledger.ParseMessage 解析訊息
  • 寫入 Firestore 記帳資料，透過 Reply API 回覆結果

② 記帳表單流程

  • 使用者從好友歡迎訊息或連結開啟 LIFF 表單（LINE 內建瀏覽器直接載入 services/liff，不經過 Messaging API webhook）
  • 每個請求都帶 LIFF ID Token，後端呼叫 LINE 的 /oauth2/v2.1/verify 驗證身份
  • POST /liff/entries 新增一筆，跟 webhook 共用 internal/store.AddEntry
  • /history 是獨立頁面，呼叫 GET /liff/entries 查歷史（支援分類/收支/日期區間篩選），跟 summary 共用同一套 ledger.Summarize 分類小計邏輯；每筆記錄可就地編輯（PUT /liff/entries/{id}，只改 amount/category/note，createdAt 不變）或刪除（DELETE /liff/entries/{id}）
  • /settings 是訂閱設定頁面，勾選每日／每週／每月（可複選），GET/POST /liff/settings 讀寫 Firestore users/{lineUserId}.subscriptions

③ 每日總結流程

  • Cloud Scheduler 每日固定時間呼叫 services/summary 的 /run（唯一的排程，週/月不是另外的 Scheduler job）
  • 沒有 webhook event、沒有 reply token，靠 base.New 已初始化好的 client 直接動作
  • 每次都跑「每日」；週一額外跑「每週」（上週一到週日）、每月 1 號額外跑「每月」（上個月整月），各自查 store.ListSubscribers(frequency) 找出訂閱該頻率的所有使用者
  • 對每個訂閱者各自查 Firestore 該區間的記帳資料，ledger.Summarize 按分類算小計，各自 Push 一則訊息——多人、多頻率都是同一支 /run 處理，沒有寫死的收件人

CI/CD

  • 三服務各自獨立的 GitHub Actions workflow，path filter 只在對應目錄變動時觸發
  • push main 才會部署，PR 只跑 build/test + lint + vulncheck
  • 用 Workload Identity Federation 認證，GitHub 不持有任何長期 GCP 金鑰
  • 詳細流程見 docs/deployment-sop.md

成本控管

  • 三個 Cloud Run 服務都 min-instances=0，無請求時不計費
  • Cloud Scheduler：免費額度每月 3 個 job，一個每日排程綽綽有餘
  • Firestore：Native mode always-free 額度（1GiB / 5萬讀 / 2萬寫 / 2萬刪 每日）
  • Artifact Registry 免費額度只有 0.5GiB，靠 cleanup policy 只留最近幾版 image
  • 另設 GCP Budget Alert 防呆

資料模型

  • users/{lineUserId}/entries/{entryId}：amount, category, note, createdAt
  • users/{lineUserId}（文件本身）：subscriptions（陣列，值是 daily/weekly/monthly 的任意組合），由 services/liff 的 /settings 頁面寫入，services/summary 用 array-contains 查詢
  • 三服務共用同一份 internal/ledger、internal/store，設定則各自從 internal/base 疊加專屬欄位
